# wave-reduce

Паралельна програма на Go, яка обчислює суму елементів масиву з 10⁹ елементів методом попарного згортання «хвилями».

## Алгоритм

На кожній хвилі елементи додаються попарно: перший з останнім, другий з передостаннім і т.д. Результат записується в доданок із меншим індексом. Після проходу до середини «актуальна» довжина масиву зменшується (друга половина відкидається), і процес повторюється, доки довжина не стане 1.

Приклад для `[1, 2, 3, 4, 5, 6]`:

| Хвиля | Пари | Актуальна частина | «Відпрацьовані» елементи |
|---|---|---|---|
| 1 | 1+6, 2+5, 3+4 | `[7, 7, 7]` | `{4, 5, 6}` |
| 2 | 7+7 | `[14, 7]` | `{7, 4, 5, 6}` |
| 3 | 14+7 | `[21]` | `{7, 7, 4, 5, 6}` |

Сума елементів: **21**.

Якщо актуальна довжина `n` непарна, середній елемент не має пари й залишається на місці. Нова довжина дорівнює `n - n/2`.

## Архітектура

```
        ┌─────────────────────────┐
        │ керуючий потік (reduce) │
        │  - ділить хвилю на      │
        │    діапазони [lo, hi)   │
        │  - чекає завершення     │
        │    хвилі (WaitGroup)    │
        └───────────┬─────────────┘
                    │ chan task
        ┌───────────┼───────────┐
        ▼           ▼           ▼
    воркер 1    воркер 2  …  воркер N      (N = кількість ядер)
```

- **Пул воркерів** фіксованого розміру (за замовчуванням `runtime.NumCPU()`), створюється один раз. Максимальну кількість потоків (по одному на пару) не створюємо через накладні витрати.
- **Керуючий потік** передає воркерам завдання через канал і синхронізує хвилі.
- **Завдання** — це діапазон індексів лівої половини `[lo, hi)`. Воркер сам обчислює симетричний індекс `n-1-i` для кожного `i`, а потім додає відповідні елементи. Діапазони, а не окремі індекси, використано, щоб зменшити накладні витрати на передачу через канал (для 5·10⁸ пар це були б десятки секунд лише на комунікацію).
- **Синхронізація хвиль** — `sync.WaitGroup` працює як бар'єр: наступна хвиля стартує лише після завершення всіх завдань попередньої.
- **Відсутність гонок даних.** У межах хвилі воркери пишуть у `a[i]` для `i < n/2`, а читають `a[n-1-i]` для індексів `≥ n/2`. Ці множини не перетинаються, тому м'ютекси не потрібні.
- **Життєвий цикл горутин.** Після останньої хвилі канал закривається, воркери завершуються, `poolWG.Wait()` гарантує відсутність витоків.

## Вимоги

- Go 1.22 або новіший
- Для `n = 1 000 000 000` потрібно близько **8 ГБ** вільної оперативної пам'яті (`int64` × 10⁹). Для меншої пам'яті використовуйте менше значення `-n`.

## Збірка та запуск

```bash
go build -o reduce .
./reduce
```

### Параметри

| Прапорець | За замовчуванням | Опис |
|---|---|---|
| `-n` | `1000000000` | кількість елементів масиву |
| `-workers` | `runtime.NumCPU()` | кількість робочих потоків |
| `-chunk` | `262144` (2¹⁸) | максимальний розмір діапазону індексів в одному завданні |

Приклади:

```bash
./reduce -workers 1                       # базова лінія для оцінки прискорення
./reduce -workers 8 -chunk 65536
./reduce -n 250000000                     # менше пам'яті
```

Масив заповнюється за правилом `a[i] = i%10 + 1`, тому еталонну суму можна порахувати за формулою й автоматично перевірити результат.

## Результат запуску

Конфігурація: `workers=12`, `chunk=262144`, `n=10⁹`.

```
n=1000000000 (~7.5 ГБ), workers=12, chunk=262144
сума:     5500000000
очікувано: 5500000000
збіг:     true
час:      724.5243ms
```

Час вимірюється лише для функції `reduce` (без виділення пам'яті та заповнення масиву).

Характеристики машини:

| Параметр | Значення |
|---|---|
| Процесор | Intel Core i5-11400H @ 2,70 ГГц |
| Ядра / потоки | 6 фізичних / 12 логічних |
| Оперативна пам'ять | 2 × 8 ГБ (16 ГБ), DDR4-3200 |
| ОС | Windows 11 (10.0.26200) |
| Версія Go | go1.27.2 windows/amd64 |

### Аналіз

Задача **memory-bound**: на кожну пару припадає два читання й один запис, а арифметики майже немає. Тому швидкодія обмежена пропускною здатністю оперативної пам'яті, а не кількістю ядер. Орієнтовна оцінка: перша хвиля читає 8 ГБ і пише 4 ГБ, наступні хвилі разом додають приблизно стільки ж. Загальний трафік пам'яті — близько 24 ГБ за 0,72 с, тобто ~33 ГБ/с, що відповідає типовій ефективній пропускній здатності двоканальної DDR4/DDR5.

Для двох планок DDR4-3200 у двоканальному режимі теоретична пропускна здатність становить 51,2 ГБ/с, тож отримані ~33 ГБ/с — приблизно 65% від максимуму, що є реалістичним значенням для практичного навантаження.

Очікувана поведінка при збільшенні `workers`: прискорення на перших 2–4 потоках, далі вихід на плато через насичення шини пам'яті.
